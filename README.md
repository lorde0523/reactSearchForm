# 조회 조건 컴포넌트

React, Ant Design, react-hook-form으로 만든 스키마 기반 조회 조건 화면입니다. 모든 소스는 JavaScript/JSX로 작성되어 있습니다.

## 실행

```bash
pnpm install
pnpm dev
```

## 조건 구성

`src/App.jsx`의 `searchRows` 배열에 행과 소제목 그룹, 입력 필드를 선언합니다.

- `row.required: true`: 기본 노출되는 필수 조회 행
- `row.required: false`: 상세조회 버튼으로 펼쳐지는 행
- `group.label`: 저장 모달 테이블의 첫 번째 컬럼 값
- `group.fields`: 다음 소제목 전까지 하나의 값 세트로 묶을 입력 항목

지원 필드 타입은 `text`, `select`, `date`, `dateRange`, `checkbox`입니다. 같은 그룹의 값이 두 개 이상이면 저장 모달의 두 번째 컬럼에 `/`로

역할

너는 대규모 React 기반 엔터프라이즈 웹 애플리케이션의 프론트엔드 아키텍트이자 시니어 개발자다.

현재 프로젝트의 소스코드를 분석하고, 기존 아키텍처를 최대한 유지하면서 800개 이상의 화면에 적용할 수 있는 **전역 브라우저 타이틀 관리 시스템(Global Title Management System)**을 설계하고 구현해 줘.

기존 코드에 대한 영향과 중복 구현을 최소화하고, 유지보수성, 확장성, 안정성을 우선해야 한다.

1. 현재 프로젝트 환경

* 프레임워크: React
* 라우팅: React Router (BrowserRouter + Routes)
* 서버 데이터 관리: TanStack Query (useQuery)
* 메뉴 정보: DB에서 관리하고 API로 조회
* 화면 규모: 800개 이상으로 확장 예정
* 새 창: window.open() 방식
* 차트: 공통 차트 컴포넌트 기반
* 기존 타이틀 설정: document.title 직접 변경
* 타이틀 관리용 추가 라이브러리 도입은 지양

React, React Router, TanStack Query의 정확한 버전과 프로젝트의 실제 구조는 소스코드를 확인해서 판단할 것.

2. 브라우저 타이틀 정책

프로젝트 전체에서 다음 4가지 정책을 반드시 준수해야 한다.

① 메인 홈 화면

Home | portal

② 일반 페이지

{페이지명} | portal

예시: 사용자 관리 | portal

③ window.open()으로 열린 일반 새 창

[새 탭] {페이지명} | portal

예시: [새 탭] 사용자 관리 | portal

④ 차트 새 창

[차트] {차트헤더명} - {페이지명} | portal

예시: [차트] 월별 사용자 현황 - 사용자 관리 | portal

타이틀 형식은 공통 Formatter에서 관리하며 개별 화면에 문자열을 하드코딩하지 않는다.

3. 핵심 요구사항

A. 전역 타이틀 관리

* GlobalTitleManager 또는 동등한 공통 관리 구조를 구현한다.
* 타이틀 결정 및 document.title 갱신을 중앙 집중화한다.
* react-helmet, react-helmet-async는 도입하지 않는다.
* 기존 BrowserRouter + Routes를 유지한다.
* 개별 페이지마다 별도 Hook을 호출하거나 타이틀 설정 코드를 작성하지 않도록 설계한다.
* URL이 변경되면 타이틀도 자동으로 변경되어야 한다.
* 각 화면 컴포넌트 수정은 최대한 피한다.

B. 페이지명 자동 조회

* 기존 DB 메뉴 API에 존재하는 메뉴명을 재사용한다.
* URL 또는 화면 ID를 기준으로 현재 페이지를 식별한다.
* 동적 경로 파라미터를 지원한다.
* 메뉴 데이터 조회는 기존 TanStack Query 구조를 재사용한다.
* 이미 존재하는 메뉴 API, Query Key, 메뉴 Store가 있다면 중복 구현하지 않는다.
* 메뉴 정보 로딩 전과 조회 실패 시 안전한 기본 타이틀을 제공한다.
* DB 메뉴에 등록되지 않은 팝업 또는 특수 화면의 처리 방안도 제시한다.

C. 새 창 타이틀 관리

* window.open()으로 열린 새 창은 메인 창과 독립적으로 타이틀을 관리한다.
* 기존 새 창 호출 구조를 분석한다.
* 일반 새 창과 차트 새 창을 명확히 구분한다.
* 가능하면 공통 새 창 실행 유틸리티를 활용한다.
* 팝업의 최초 실행, 새로고침, 내부 라우팅 변경을 고려한다.
* window.opener, sessionStorage, URL 파라미터 등을 사용할 경우 부작용을 검토한다.
* 특히 sessionStorage가 opener로부터 초기 복사될 수 있다는 점을 고려해 창 유형이 잘못 전파되지 않도록 한다.
* 새 창을 여러 개 동시에 열더라도 타이틀이 서로 간섭하지 않아야 한다.

D. 차트 헤더명 연동

차트 새 창의 타이틀에 실제 차트 헤더명을 반영해야 한다.

요구사항:

* 기존 공통 차트 컴포넌트의 구조를 우선 분석한다.
* 차트 헤더가 props, API 응답, TanStack Query 중 어디에서 생성되는지 파악한다.
* 가능하면 공통 차트 컴포넌트 한 곳만 수정한다.
* 800개 화면 각각에 차트 타이틀 코드를 추가하지 않는다.
* 차트 헤더가 동적으로 변경되면 브라우저 타이틀도 갱신한다.
* 차트 헤더가 아직 로딩되지 않았다면 적절한 기본값을 사용한다.
* 여러 차트가 동시에 존재하는 경우 현재 열린 차트의 헤더만 반영해야 한다.
* 차트 헤더가 포함하는 데이터의 민감성을 고려하고, 불필요하게 URL에 노출하지 않는다.

E. 성능 및 유지보수

* 화면 전환 시 불필요한 전체 앱 재렌더링을 방지한다.
* 타이틀 변경을 위해 별도의 중복 API 요청을 발생시키지 않는다.
* TanStack Query의 전체 캐시를 구독하는 방식은 명확한 필요가 있을 때만 적용한다.
* 기존 공통 컴포넌트와 유틸리티를 최대한 재사용한다.
* React Hook 사용 규칙을 준수한다.
* 타입스크립트를 사용 중이라면 기존 타입 정의와 패턴을 준수한다.
* 새 라이브러리 설치는 최소화한다.

4. 우선 분석할 코드

실제 코드베이스를 탐색하여 다음 사항을 확인해 줘.

1. React 및 관련 라이브러리 버전
2. App 및 최상위 Provider 구조
3. BrowserRouter, Routes, 공통 Layout 구성
4. DB 메뉴 API와 메뉴 데이터 구조
5. URL과 화면 ID를 매핑하는 기존 로직
6. document.title을 변경하는 모든 위치
7. window.open()을 호출하는 기존 공통 함수 및 개별 호출부
8. 새 창 또는 팝업을 렌더링하는 공통 구조
9. 공통 차트 컴포넌트와 차트 헤더 생성 방식
10. 기존 TanStack Query의 활용 패턴

이미 구현되어 있는 기능을 새로 만들지 말고, 반드시 기존 구조에 통합할 것.

5. 설계 원칙

다음 우선순위를 따른다.

1. 기존 코드 변경 최소화
2. 화면별 중복 코드 제거
3. 타이틀 정책 중앙 집중화
4. 메인 창과 새 창의 독립성
5. 동적 차트 헤더 지원
6. 성능 및 안정성
7. 신규 화면 자동 적용

기본 페이지 타이틀을 생성하기 위해 화면마다 별도의 설정 파일이나 메타데이터를 추가하는 방식은 피한다.

기존 메뉴 API로 해결할 수 있는 부분은 반드시 재사용한다.

동적 데이터가 반드시 필요한 경우에만 최소한의 공통 인터페이스를 추가한다.

6. 작업 순서

1단계: 기존 프로젝트 분석

관련 코드를 조사하고 현재 구조를 설명한다.

2단계: 최적 아키텍처 제안

현재 구조에 적합한 최소 변경 방식을 제안한다.

새로운 전역 상태 관리 라이브러리나 불필요한 추상화 계층은 만들지 않는다.

3단계: 구현

분석 결과를 토대로 실제 프로젝트에 통합 가능한 코드를 작성한다.

코드가 현재 프로젝트의 폴더 구조와 네이밍 규칙을 따르도록 한다.

4단계: 테스트 및 검증

다음 상황을 검증한다.

* 홈 화면 접속
* 일반 페이지 이동
* 일반 새 창 실행
* 차트 새 창 실행
* 차트 헤더 변경
* 새 창 새로고침
* 새 창 내부 라우팅
* 여러 새 창 동시 실행
* 메뉴 API 로딩 및 실패
* 존재하지 않는 화면 ID
* 기존 타이틀 처리 코드와 충돌

7. 최종 결과물

다음 순서로 결과를 제공해 줘.

1. 기존 프로젝트 구조 분석 결과
2. 현재 구조의 문제점
3. 추천 아키텍처와 데이터 흐름
4. 수정 또는 추가해야 하는 파일 목록
5. 파일별 실제 구현 코드 또는 변경 사항
6. 기존 코드 대비 변경 범위
7. 테스트 시나리오
8. 향후 화면이 800개 이상으로 증가할 때의 유지보수 전략

8. 반드시 지킬 사항

* 기존 코드를 확인하지 않고 파일명, API 경로, 변수명을 임의로 가정하지 말 것.
* 기존 기능을 훼손하지 말 것.
* 기존 컴포넌트를 수정하지 않아도 되는 방법을 최우선 검토할 것.
* 불필요한 라이브러리를 제안하지 말 것.
* 화면마다 document.title 또는 usePageTitle()을 추가하는 방식은 제안하지 말 것.
* 가능하면 공통 파일 몇 개만 추가하거나 수정하는 방식으로 구현할 것.
* 기존 구조로 해결할 수 없는 요구사항은 이유와 최소 변경 대안을 명확하게 설명할 것.
* 단순한 예시 코드보다 실제 프로젝트에 적용할 수 있는 구현을 우선할 것.

가장 중요한 목표는 800개 화면의 제목을 개별 관리하는 것이 아니라, 기존 메뉴 정보와 공통 컴포넌트를 활용해 메인 화면·일반 페이지·새 탭·차트 팝업의 타이틀을 자동으로 관리하는 것이다.

먼저 실제 코드를 분석하고, 확인된 구조에 근거하여 가장 수정 범위가 작은 방안을 제안해 줘. 코드베이스 접근이 가능한 경우 변경 작업까지 수행하고, 접근이 불가능하다면 분석에 필요한 파일을 구체적으로 요청해 줘.






앞서 분석한 프로젝트 구조를 기준으로 실제 구현을 진행해 줘.

다음 조건을 추가로 준수해.

1. 공통 타이틀 관리에 필요한 파일만 수정한다.
2. 기존 800개 화면의 컴포넌트는 최대한 수정하지 않는다.
3. 기존 메뉴 API와 공통 차트 컴포넌트를 재사용한다.
4. 기존 window.open 처리 방식과 호환성을 유지한다.
5. 수정한 파일별 변경 사항과 변경 이유를 명시한다.
6. 실제로 확인되지 않은 함수, 타입, API를 임의로 생성하지 않는다.
7. 컴파일 및 타입 검증이 가능하면 실행하고 결과를 보고한다.
8. 기존 동작에 영향을 줄 수 있는 부분과 테스트가 필요한 부분을 구분한다.

코드를 과도하게 추상화하지 말고, 가장 단순하면서 확장 가능한 방식으로 구현해 줘.
